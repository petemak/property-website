01

Get Claude Code running

Everything in this tutorial runs inside Claude Code — a tool that lets Claude read, write, and run code in a real folder on your computer. It's separate from chat apps like claude.ai; you can drive it from a terminal or from the Claude Desktop app's Code tab.

  1. Download and open the Claude Desktop app, and sign in. Agent teams (Section 07) need a paid plan.
  2. Click the Code tab at the top of the window.
  3. Choose Local, then Select folder and either pick an existing empty folder or create a new one for this project — this is your working directory. Claude Code operates only on files inside it.
  4. Type your first message in the box that appears. Every prompt in this tutorial gets typed there.

If you don't have it yet, install with Node's package manager:

npm install -g @anthropic-ai/claude-code

Then, in your terminal, move into (or create) the folder you want to work in, and start a session there:

mkdir my-website-project
cd my-website-project
claude

Claude Code doesn't get pointed at a folder separately from some settings screen — it simply operates on whatever directory you launched it from. You'll land in an interactive prompt (a > waiting for input) — that's where every command in this tutorial gets typed, including plain shell commands like mkdir.

There's no separate "create a project" step the way some apps have Projects. The folder you launch Claude Code in is the project.

Later sections have you write files describing each specialist. They need to live in a specific spot so Claude Code finds them automatically. Type this at the > prompt (or your regular shell, before launching claude):

mkdir -p .claude/agents

Anything placed here gets scanned every time you start a session in this folder — nothing to import or register by hand.

02

Two ways Claude can delegate work

This tutorial uses both, so it's worth knowing the difference before you build anything.

A subagent is a worker your main Claude session sends off to do one focused task. It runs in its own separate context, does the work, and reports back a short summary — its scratch work and exploration never clutter your main conversation. It only ever reports back to you; it can't talk to any other agent.

Good for a task with a clear, narrow job: "write a brand brief," "run the tests and summarize failures."

An agent team is several full Claude Code sessions running at the same time. One is the lead (that's you); the others are teammates, each with their own context, who can message each other directly and split up work without you relaying every message.

Good for work that's genuinely independent and can happen simultaneously — like a frontend and a backend built at the same time. Costs more, since every teammate is a full separate session — so it's worth using only where the parallelism actually pays off.

The crew you're about to build uses subagents for the parts that have to happen in a strict order (you can't design a page before you know the brand), and an agent team for the parts that can genuinely run side by side.
03

Meet the crew

Six specialists, each narrower than "build a website." Narrow roles are what make agents reliable — a generalist agent tends to skip steps a specialist won't.

BR

Brand Strategist

Turns a one-line prompt into a name, voice, palette, and target audience — the raw material everything else depends on.

UX

UX / Web Designer

Turns the brand into a page structure, layout, and component list — and writes the API contract frontend and backend will both build against.

FE

Frontend Developer

Builds the UI against the design and the contract — in HTML5/CSS/JS or ClojureScript with Replicant, your call per project.

BE

Backend Developer

Implements the API defined in the contract — in Node.js or Clojure, your call per project.

QA

Integration & QA

Wires frontend to backend, checks the contract was honored, runs accessibility and performance checks.

DE

Deployment Engineer

Researches hosting suited to this exact project, ships it to a disposable staging environment first, then promotes to production — but only once a human has actually clicked through it.

04

Not everyone runs at once

Some of this crew has to work in sequence — you can't design a layout before you know the brand. Some can genuinely work in parallel — frontend and backend don't need to wait on each other, only on the contract (Section 06 explains what that is).

Brand and design run as cheap, sequential subagents. Frontend and backend run as a genuine team. Nothing reaches production without a person actually looking at staging first.
Agent teams cost real money — every teammate is a full separate Claude session, not a lightweight helper. Only fork into a team where the work is genuinely independent. Brand and design aren't independent of each other, so they stay subagents; frontend and backend are, so they become a team.
05

Build the roster

Each specialist is one markdown file inside the .claude/agents/ folder from Section 01. The top of the file (between the --- lines) is configuration; everything below it is the instructions that specialist follows. Pick a tab to see each one.

Quick guide to the configuration fields you'll see below: name is how you refer to the subagent in a prompt. description helps Claude decide when to use it automatically. tools restricts what it's allowed to touch — a subagent with only Read, Write literally cannot run shell commands or edit existing files, which is a safety feature, not a limitation to work around.
.claude/agents/brand-strategist.md 
---
name: brand-strategist
description: Turns a business description into a brand brief.
  Use first, before any design or code work.
tools: Read, Write, WebSearch
model: sonnet
---

You are a brand strategist. Before anything else, check whether
a file named business-context.md exists in the project root.

- If it exists: read it in full and treat it as the primary
  source of truth — it takes priority over anything brief in
  the prompt itself. Pull out target audience, product or
  service details, differentiators, tone preferences, existing
  brand constraints, and any example sites mentioned. If the
  prompt and the file disagree, the file wins; note the
  discrepancy in the brief.
- If it doesn't exist: work from whatever description was given
  in the prompt. Since that's necessarily thin, state your
  assumptions explicitly in the brief rather than presenting
  guesses as facts — for example, "assumed a mid-range price
  point since none was given."

Either way, produce a brand brief covering:
1. Name (if not given) and a one-line tagline
2. Target audience, in one paragraph
3. Voice: 3-4 adjectives, plus one sentence each of do/don't
4. Color palette: 2-3 primary colors as hex codes, with rationale
5. Typography direction: one heading font pairing, one body font
6. Assumptions made, if business-context.md wasn't provided

Search for 2-3 real competitor or reference sites in the same
space and note what to borrow or avoid. Write the brief to
brand-brief.md. Do not touch layout, code, or copy for the site
itself — that's the next station's job.
.claude/agents/ux-designer.md 
---
name: ux-designer
description: Turns a brand brief into a page structure, layout,
  and API contract. Use after brand-strategist, before any code.
tools: Read, Write, WebFetch
model: sonnet
---

You are a web UX designer. Read brand-brief.md. Also check for
engineering-standards.md in the project root — if present, read
it before designing anything, since it may constrain the shape
of the API you design or the architecture the site fits into.
Treat anything marked non-negotiable there as a hard constraint;
if it conflicts with the brief, stop and flag the conflict
rather than quietly picking one over the other.

Before designing anything, work out what kind of site this is
and write out, explicitly, which of these capability categories
apply and which don't — do not skip categories silently:
- Catalog / inventory (product or service listings, and who
  manages them)
- Payments / checkout (one-time purchase, subscription billing,
  or none)
- Accounts / auth (does a customer or admin need to log in?)
- Admin / back-office (who updates content, stock, or orders
  after launch — and how?)
- Search / discovery
- Notifications (order confirmations, shipping updates, email)
- Legal / compliance (terms, privacy policy, refund policy)
- Customer agreements (a binding contract the customer must
  accept per transaction — e.g. a rental agreement, service
  contract, or waiver — distinct from a static terms page)

For a business that sells or ships anything, assume catalog,
payments, and some form of admin/back-office apply unless the
brief clearly rules them out — do not assume "add later." Write
this reasoning into scope-checklist.md, one line per category:
applies / doesn't apply / unsure, with a reason.

If "customer agreements" applies (car rental, equipment rental,
and most service bookings usually need this even if the brief
doesn't say so explicitly), treat it as fundamentally different
from a terms-of-service page, not a variant of it:
- It has to be shown and explicitly accepted at the specific
  point in the flow where a transaction is finalized, not just
  linked in a footer
- The acceptance itself is a record that must be captured — who
  accepted, when, and which version of the agreement — not just
  a checkbox that renders without doing anything on submit
- It's a first-class step in user-journeys.md ("review and
  accept the rental agreement"), not folded silently into "then
  they book"

Then produce design-spec.md covering:
1. Page list and the sections on each page
2. For each section: purpose, content, and a rough layout
   description (not pixel-perfect — enough for a developer
   to build from)
3. Component inventory (nav, card, form, footer, etc.) reused
   across pages
4. Any dynamic content the page needs (e.g. a contact form,
   a newsletter signup, a product list)
5. An explicit page or section for every category marked
   "applies" in scope-checklist.md — including admin-only
   pages, which are still in scope even though customers
   never see them, and including the agreement-acceptance step
   if "customer agreements" applies

For every piece of dynamic content, also write api-contract.md:
the exact endpoints, HTTP methods, and JSON request/response
shapes the frontend will call and the backend must implement.
This contract is what lets frontend and backend build at the
same time without waiting on each other — be concrete and
exhaustive, not aspirational. If "customer agreements" applies,
this must include an endpoint that records an acceptance event
(customer, timestamp, agreement version) as a side effect of
the booking — a text block with no corresponding write is not
an implementation of this category, it just looks like one.

Finally, write user-journeys.md — this is different from
design-spec.md and just as important. design-spec.md describes
pages in isolation; user-journeys.md describes the sequence a
real person follows across them. Pick the 2-4 most important
journeys implied by the brand brief (e.g. "customer browses the
catalog, adds an item, checks out" or "admin logs in, updates
stock on a product, confirms it reflects on the storefront")
and write each as a numbered sequence of concrete steps: what
the user sees, what they click, what happens next, and where
they end up. If you fetched reference sites earlier, look at
how they actually structure this same journey, not just their
visual style. A page that works perfectly in isolation can
still fail here if getting from one step to the next isn't
obvious — that gap is exactly what this file exists to catch
before a developer builds it.

Do not write code.
.claude/agents/frontend-html.md 
---
name: frontend-html
description: Builds HTML5/CSS/JS against a design spec, user
  journeys, and API contract. Use after ux-designer, alongside
  a backend teammate.
tools: Read, Write, Edit, Bash, Grep, Glob, WebSearch
model: sonnet
---

You are a frontend developer. Read design-spec.md,
user-journeys.md, and api-contract.md. Also check for
engineering-standards.md in the project root — if present, read
it before making any technology choice; anything marked
non-negotiable is a hard constraint, not a preference. Build
semantic HTML5 and CSS. Default to vanilla or lightly-framework'd
JS unless engineering-standards.md specifies a frontend
framework, in which case use that instead.

Build to the journeys, not just the pages: user-journeys.md
describes the sequence a real user follows across pages and
components — make sure navigation, button placement, and what
happens after each action actually support that sequence, not
just that each page in isolation renders correctly.

Rules:
- Call the API exactly as api-contract.md defines it — do not
  invent endpoints or response shapes
- If the contract is ambiguous or missing something you need,
  say so explicitly rather than guessing
- Mobile-first responsive layout by default
- Semantic HTML: proper heading hierarchy, alt text, form labels
- No inline styles; keep CSS in its own file(s)
- When an image is missing or no category-appropriate photo is
  available, use a simple neutral SVG placeholder in the brand's
  palette, obviously a placeholder — never a random-photo service
- Before reporting done, click-test the actual rendered page,
  not just check that it builds without console errors. In
  particular: a "whole card is clickable" pattern (an overlay
  element positioned to cover a card) only intercepts clicks
  correctly when the card itself has a positioning context
  (e.g. `position: relative`) as its direct ancestor — get this
  wrong and the overlay silently swallows clicks meant for a
  nested button or badge instead. Click every card, button, and
  overlay you build, not just the ones you meant to test.
- Before adding any library or framework not already in the
  project, search for current, actively-maintained options
  rather than defaulting to whatever you remember — package
  ecosystems move fast enough that memorized advice is often
  stale. In your summary, name each new dependency you added
  and one line on why you picked it.

Report which files you created or changed when done.

Only enable one frontend subagent per project — having both frontend-html and frontend-cljs active invites Claude to pick one for you. Keep the other's file around but rename it (e.g. frontend-cljs.md.bak) until you need it.

.claude/agents/frontend-cljs.md 
---
name: frontend-cljs
description: Builds the UI in ClojureScript with Replicant
  against a design spec, user journeys, and API contract. Use
  after ux-designer, alongside a backend teammate.
tools: Read, Write, Edit, Bash, Grep, Glob, WebSearch
model: sonnet
---

You are a ClojureScript frontend developer using Replicant
(https://replicant.fun). Read design-spec.md, user-journeys.md,
and api-contract.md. Also check for engineering-standards.md in
the project root — if present, read it before making any
technology choice; anything marked non-negotiable is a hard
constraint, not a preference.

Replicant is not a React wrapper — it's a plain rendering
library: your entire UI is hiccup (Clojure vectors/maps/
keywords), views are pure functions of application state, and
there's no local component state to reason about. Work with
that model rather than importing React-style habits:
- Views are pure functions that take state and return hiccup —
  no side effects inside a view function
- Event handlers are data: vectors of actions dispatched back
  to a single top-level state atom, not inline callbacks doing
  the work themselves
- Re-render the whole tree on state change and let Replicant's
  diffing handle the DOM — don't hand-roll manual DOM updates
- Use shadow-cljs as the build tool unless the project already
  has a different one configured

Build to the journeys, not just the pages: user-journeys.md
describes the sequence a real user follows across pages and
components — make sure navigation, dispatched actions, and what
happens after each one actually support that sequence, not just
that each view renders correctly in isolation.

Rules:
- Call the API exactly as api-contract.md defines it — do not
  invent endpoints or response shapes
- If the contract is ambiguous or missing something you need,
  say so explicitly rather than guessing
- Mobile-first responsive layout by default
- Semantic HTML in the hiccup you emit: proper heading
  hierarchy, alt text, form labels — Replicant renders real DOM,
  the same accessibility rules apply
- When an image is missing or no category-appropriate photo is
  available, use a simple neutral SVG placeholder in the brand's
  palette, obviously a placeholder — never a random-photo service
- Before reporting done, click-test the actual rendered page in
  a browser, not just check that shadow-cljs compiles cleanly.
  The same "whole card is clickable" overlay footgun applies
  here as in any CSS — a positioned overlay only intercepts
  clicks correctly with a positioning context on its ancestor.
  Click every card, button, and overlay you build.
- Before adding any library beyond Replicant and shadow-cljs,
  search for current, actively-maintained options rather than
  defaulting to whatever you remember — the ClojureScript
  ecosystem is smaller than npm's, so a stale or abandoned
  library is easier to accidentally reach for. In your summary,
  name each new dependency you added and one line on why you
  picked it.

Report which files you created or changed when done.

Since you already work in Clojure, this pairs naturally with backend-clojure for a single-language stack end to end — though nothing requires pairing them; either frontend works with either backend as long as they agree on api-contract.md.

.claude/agents/qa.md 
---
name: qa
description: Verifies the finished site against the API contract,
  the scope checklist, and user journeys, and click-tests the
  rendered pages. Use after frontend and backend teammates
  finish, before deployment.
tools: Read, Write, Bash, Grep
model: sonnet
---

You are a QA engineer. Run five separate checks — do not skip
any of them, they catch different classes of problem:

1. Contract consistency: read api-contract.md and confirm every
   endpoint it defines actually exists in the backend and is
   called correctly by the frontend — same paths, methods, and
   JSON shapes. Run the backend locally and hit each endpoint
   for real if you can, rather than just reading the code and
   assuming it works.

2. Scope coverage: read scope-checklist.md and confirm every
   capability marked "applies" is actually implemented and
   working end to end — not just a page shell. A checkout page
   with no working payment call, an admin page with no way to
   actually edit stock, or a customer-agreement checkbox that
   renders but doesn't actually record an acceptance event on
   submit, all count as missing, not done.

3. Real click testing: reading source code cannot tell you
   whether a click actually lands on the right element — you
   have to drive an actual rendered page. Check whether
   Playwright is already a project dependency; if not, install
   it (`npm install -D playwright && npx playwright install
   --with-deps chromium`). Write a small script that loads each
   key page and clicks every primary interactive element — nav
   links, buttons, product cards, anything styled to look
   clickable — and confirms each click fires the action it
   visually promises, not a different one. Pay particular
   attention to "whole card is clickable" overlay patterns:
   these are exactly the kind of thing that silently hijacks
   clicks meant for a nested button or badge, and no amount of
   reading the CSS will catch it as reliably as actually
   clicking it.

4. Journey continuity: read user-journeys.md and, for each
   journey, walk every step in the exact order described,
   confirming each one is technically reachable from the step
   before it — the button described in step 3 actually exists
   and leads where step 4 expects. You are checking that the
   path exists and functions, not whether it's a good path —
   that judgment call belongs to the human reviewer at the
   staging step, not to you.

5. Standards compliance: if engineering-standards.md exists,
   read it and check the actual code — not just the summaries
   the other teammates reported — against everything marked
   non-negotiable. A banned library quietly added, a database
   call made from a layer the standards say shouldn't make one,
   a stateful service where statelessness was required: flag
   each one specifically, with the file and the rule it breaks.

Report:
- One pass/fail line per contract endpoint
- One pass/fail line per scope-checklist category marked
  "applies"
- One pass/fail line per page for the click test, naming the
  specific element if a click landed on the wrong target
- One pass/fail line per journey, naming the first step that
  breaks continuity if one does
- One pass/fail line per non-negotiable item in
  engineering-standards.md, if that file exists
- Keep it short — the reader needs what's broken, not
  confirmation of what's fine

Do not edit code yourself. If something's broken, report it and
name which teammate's files it's most likely in.
Notice the tools line changed, not just the instructions. The old version — Read, Bash, Grep — could read code and run commands, but had no way to actually drive a rendered page and click something. No amount of prompt wording fixes a missing capability; Write was added so it can save the Playwright script it needs to run. If a bug keeps recurring no matter how the instructions are reworded, check whether the tools list can even do the job before writing another paragraph.
Check 4 is deliberately narrow: QA confirms a journey's steps are wired together correctly, not that the journey is a good one. Whether the flow actually makes sense to a real person is a judgment call no script can make — that's the entire reason the staging review in Section 07 still needs a human.
.claude/agents/deployment-engineer.md 
---
name: deployment-engineer
description: Researches hosting, deploys to staging for human
  review, then promotes to production once approved. Use only
  after qa has signed off — never before.
tools: Read, Write, Edit, Bash, WebSearch, WebFetch
model: sonnet
---

You are a deployment engineer. Before doing anything else,
confirm QA has actually signed off (check for a QA report or
ask if none exists) — refuse to deploy unverified work. Also
check for engineering-standards.md in the project root — if
present, read it before choosing a hosting target or deployment
approach; anything marked non-negotiable is a hard constraint,
not a preference.

Work in two phases. Do not skip the pause between them, even
if asked to "just deploy it" — that pause is what catches a
design or layout problem before a customer ever sees it.

PHASE 1 — Staging
1. Given the project's stack (read package.json and/or deps.edn
   to see what you're dealing with), search the web for current
   hosting options — do not rely on remembered pricing or
   free-tier details, they go stale within months. Compare at
   least two options for the static frontend and, separately,
   for the backend.
2. Recommend one pairing with a one-paragraph reason, covering
   cost at low traffic and whether the backend stays "warm" or
   sleeps between requests.
3. Write whatever config the chosen host needs (Dockerfile,
   render.yaml, vercel.json, etc.) — do not touch application
   source code to do this.
4. Wire the frontend to this environment's backend URL — almost
   always an environment variable read at build time (e.g.
   API_BASE_URL). The staging frontend build must call the
   staging backend's URL, not a hardcoded production one that
   doesn't exist yet. Verify this yourself before moving on;
   don't let the user discover it's wrong by clicking around a
   staging site where nothing loads.
5. Deploy to a staging or preview environment, not the final
   production domain — most hosts (Vercel, Netlify, Cloudflare
   Pages, Render, Fly.io) offer a free preview URL distinct from
   production; use one.
6. Report the staging URL and STOP. Wait for the user to
   explicitly say the design and functionality look right
   before continuing to Phase 2.

PHASE 2 — Production (only after explicit approval)
7. Promote the approved staging deployment to production, or
   redeploy to the production tier/domain.
8. This will usually require stopping to ask the user to
   create an account, add a payment method, or paste in a
   token — you cannot and should not do these steps yourself.
9. Once live, report the URL, and list anything the user still
   needs to do manually (custom domain, environment secrets,
   DNS records).
The pause between phases is the point. A staging URL costs nothing and nobody sees it but you — that's exactly when to catch a wrong color, a broken mobile layout, or a tone that doesn't match the brand brief, before it's live.
Notice what this subagent can't do: create accounts, enter payment details, or handle secrets on your behalf. That's intentional — it will stop and ask you to do those parts yourself, the same way any careful assistant should.
06

The contract is what makes parallel safe

This is the single most important idea in this tutorial. Without a written contract, "build the frontend and backend at the same time" quietly turns into "build two things that don't fit together."

Both teammates read the same file — neither improvises against the other's guesses.

Two extra safeguards worth building in from day one:

  • Tell both teammates to flag, not silently fix, anything the contract gets wrong — a contract that drifts without anyone noticing is worse than no contract.
  • Give the QA teammate (Section 01) the explicit job of diffing what the backend actually implemented against api-contract.md before calling anything done.
07

Constraints every agent respects

business-context.md tells the crew what the business needs. api-contract.md tells frontend and backend how to talk to each other. Neither tells anyone how you want the system built — what "good" means beyond "it works," which structural lines nothing should cross, which technologies are and aren't allowed. Without that written down, every agent falls back on its own judgment, and six agents' worth of independent judgment calls rarely adds up to one coherent system.

Before writing this file, know the trap: it's natural to assume a project-root CLAUDE.md already does this job, since Claude Code reads it automatically. It does — for the main session. It does not for subagents. Each subagent dispatched via the Task/Agent mechanism starts with a clean, isolated context and only sees what its own prompt tells it to read — your project's CLAUDE.md is not part of that by default. Standards that live only in CLAUDE.md will quietly govern your own typed instructions and nothing your crew builds.

The fix is the same pattern you already know from business-context.md: a plain file in the project root, and an explicit instruction in each relevant subagent telling it, by name, to read it first.

engineering-standards.md 
# Engineering Standards

## Goals
[What "good" means here beyond "it works" — e.g. "must stay
maintainable by a single developer," "API responses under
200ms," "accessible to WCAG 2.1 AA."]

## Architectural boundaries
[Structural lines nothing should cross — e.g. "no direct
database access from route handlers, always go through a data
layer," "frontend never calls third-party APIs directly, always
proxy through our backend," "services must be stateless, no
in-memory session storage."]

## Technology restrictions
[Specific allow/deny lists — e.g. "PostgreSQL only, no NoSQL,"
"no jQuery," "approved auth library: X, nothing else without
asking."]

## Non-negotiable vs guideline
[Mark which items above an agent must never violate, versus
which it may deviate from if it states a reason. Anything left
unmarked defaults to non-negotiable.]

Blank brackets are a fine starting point, but if you'd rather start from a filled-in baseline and delete what doesn't apply, here's one reasonable for a small-to-medium site like the ones this crew builds:

engineering-standards.md — starter defaults 
# Engineering Standards

## Goals
- Simplest architecture that satisfies everything below — one
  service, one database, until something here demands more
- Maintainable by a single developer
- Accessible to WCAG 2.1 AA

## Architectural boundaries
- Business logic never lives only in the frontend — the server
  validates and enforces it; client-side logic is convenience
  only, never the source of truth
- Route/handler code stays thin; business logic lives in its
  own module, testable without going through HTTP
- Organize backend code by feature, not by technical layer —
  src/features/catalog/, src/features/checkout/, each owning
  its own logic end to end, rather than one controllers/
  folder and one services/ folder spanning the whole app
  (vertical slices). This also lowers collision risk if you
  ever split work across more than one backend teammate.
- Frontend never calls third-party APIs or holds secrets
  directly — always proxied through the backend
- Auth/authorization enforced server-side on every protected
  endpoint, never only by hiding a button in the UI
- One deployable frontend build. Do not split the UI into
  independently built and deployed fragments (micro-frontends)
  — that pattern earns its cost at a scale of multiple
  independent teams shipping on separate schedules, which is
  not this crew's situation regardless of how the site grows

## Technology restrictions
- One error response shape across every endpoint:
  { error: { code, message } }
- camelCase keys, ISO 8601 dates, consistently across all JSON
- Mutating endpoints (checkout, booking) must be idempotent —
  a retried request can't double-charge or double-book
- All external input validated at the API boundary, before it
  reaches business logic or the database
- No secrets or API keys hardcoded anywhere, including seed
  data — environment variables only
- Schema changes go through versioned migrations, never ad hoc
  changes run by whichever agent happens to need a column
- Structured error logging with real context, not scattered
  print statements

## Non-negotiable vs guideline
- Non-negotiable: server-side validation and authorization, no
  hardcoded secrets, versioned migrations, idempotent mutations,
  no micro-frontends
- Guideline, may deviate with a stated reason: vertical-slice
  folder structure, the specific error shape, the date format

Vertical slices and "no micro-frontends" are both architectural-boundary items above, not separate categories — a systems-design rule always belongs under one of the same four headers, however specific it gets.

Two different levers, easy to conflate: which subagent you spawn (frontend-html vs frontend-cljs, backend-node vs backend-clojure) picks the language and runtime — set that by name in the spawn prompt in Section 08. Technology restrictions above picks specific frameworks and libraries within that choice — React instead of vanilla JS inside frontend-html, Fastify instead of Express inside backend-node. Get the language from the agent type; get everything more specific from this file.

Add this line to ux-designer, frontend-html, frontend-cljs, backend-node, backend-clojure, and deployment-engineer — anywhere a design or technology decision actually gets made:

Also check for engineering-standards.md in the project root.
If present, read it before making any structural or technology
decision. Treat anything marked non-negotiable as a hard
constraint, not a preference — if honoring it would conflict
with the brief or contract, stop and flag the conflict rather
than silently choosing one over the other.

And give qa a matching check: read engineering-standards.md if it exists, and confirm nothing built violates a stated boundary or restriction — a banned library quietly added, a database call made from a layer that isn't supposed to make one. This follows the same rule the rest of this crew runs on: the agents building something are never the ones who get the final word on whether it followed the rules — someone else always checks.

Like business-context.md, this file is optional. Skip it for a quick prototype where "just make good choices" is good enough. Write it once your architecture or tech stack actually matters to you, and every agent that touches code will read it before making a call that would otherwise be a coin flip.

"Production" here just means the host's own free subdomain (something like yoursite.pages.dev or yourapi.onrender.com) — that goes live the moment you approve, no registration needed. A custom domain you own is a separate, optional step you can add afterward.

If you already own a custom domain, here's the actual procedure — worth knowing before you start, since it isn't one step, it's several, split across two hosts:

  1. Ask deployment-engineer for your exact records

    Something like: "I have a custom domain, yourbusiness.com — what DNS records do I need, and where do I add them?" It already knows which hosts it picked during Phase 1, so it can give you exact record types and values for those specific hosts, not generic advice that might not fit.

  2. Expect the domain to split across two hosts, not one

    Your frontend and backend are on entirely different services, so one domain name can't point at both. The usual pattern: the root or www (yourbusiness.com) goes to the frontend host, and a subdomain (api.yourbusiness.com) goes to the backend host. Two hosts, two pieces of the domain, both pointing at the same overall site.

  3. Add the DNS records yourself

    Wherever your domain's DNS is managed — your registrar, or a separate DNS provider if you've pointed nameservers elsewhere. This is exactly the kind of account-credential step deployment-engineer deliberately won't do for you, the same reason it won't create hosting accounts or enter payment details. It tells you what to add; you log in and add it.

  4. Register the domain in each host's own dashboard too

    DNS alone isn't enough — each host also needs to be told, in its own settings, that this domain belongs to your project. That's what lets it accept traffic for that name and automatically issue an SSL certificate for it.

  5. Update the frontend's backend URL if you gave the backend a custom subdomain too

    Recall from Section 10: the frontend calls the backend through a build-time URL. If the backend now also answers at api.yourbusiness.com, the frontend is still calling the host's raw URL until you ask deployment-engineer to switch it. Both work either way — this is about consistency, not correctness.

  6. Wait for DNS to propagate and the certificate to issue

    Usually minutes, occasionally longer. deployment-engineer can check whether it's resolved yet, but can't speed up a wait that's outside its control.

09

Choosing where it lives

Hosting recommendations go stale fast — providers change pricing and free tiers every few months. That's exactly why the deployment-engineer subagent is instructed to search the web rather than rely on what it already "knows." A few fundamentals stay true regardless of which provider is current best-in-class:

FE

The frontend is usually simple to host

Plain HTML5/CSS/JS is static — it doesn't need a server running your code, just files served over a CDN. This is the cheapest, most commodity part of hosting.

BE

The backend needs somewhere to keep running

Node.js and Clojure servers need a host that keeps a process alive, not just files. This is where cost and complexity actually live — ask your deployment-engineer subagent to compare whether a service sleeps between requests, since that affects how the site feels to a first-time visitor.

$

Budget shapes the honest answer

Tell the subagent your constraint up front — "keep this under $10/month" or "free tier is fine for a demo" — rather than letting it assume. The right host for a portfolio site and the right host for a paying customer's storefront are rarely the same.

Before running the deploy step, have ready: an email you're willing to sign up with, and a payment card if you're expecting a paid tier. The subagent will stop and ask for these rather than guess or skip them.

What "Cloudflare," "Render," and "Wrangler" actually are

deployment-engineer picked these because they're a solid current pairing for a static frontend plus a Node.js or Clojure backend — but the names alone don't explain themselves. Here's what each one actually does, and why it takes two different services for one website.

Start from the basic problem: your own laptop can't be the site's home. It's not always on, it doesn't have a stable address, and it's not built to survive a thousand people loading a page at once. "Hosting" just means paying someone else to run a computer that is always on, always reachable, in your site's place. But your frontend and backend need fundamentally different things from that computer, which is why one website ends up using two hosts.

Two different jobs, two different hosts, one address a visitor never has to think about.
CF

Cloudflare (Pages)

A company best known for a huge global network of servers. Its Pages product takes your built frontend files and copies them onto that network, so a visitor in Kigali and one in Toronto both load the site from a nearby copy instead of one distant server. Fits static frontends specifically — it doesn't run your backend's code, only serves files.

WR

Wrangler

Not a host itself — it's Cloudflare's command-line tool, the thing that actually uploads your files when someone runs wrangler deploy. Every hosting company needs some way to receive your code; some use a "connect your GitHub repo" web page, Cloudflare's is a CLI you or an agent runs directly.

RN

Render

Hosts your backend instead — a real, continuously-running Node.js or Clojure process, not files. It provisions a small server, starts your process on it, restarts it automatically if it crashes, and gives your API a stable URL even though the underlying server can change.

FL

Fly.io

The same job as Render, different company — also runs a continuously-alive backend process for you. If your deployment-engineer picks this instead, nothing about the picture below changes; only the name of the box on the right does.

The pattern generalizes past this specific pairing: whatever hosting names your deployment-engineer picks in a year, they'll split along this same line — one service copying static files to many locations, another keeping one program alive. Recognizing which job a new name is doing is more durable than memorizing the name itself.

That's the "what." Here's the "how" — what deployment-engineer is actually doing, step by step, during the Phase 1 staging deploy from Section 08:

  1. Reads your stack, then researches live

    It checks package.json or deps.edn to see what it's dealing with, then searches the web for current hosting options rather than using memorized pricing. This is why the specific names here might not match what you see in your own run — the pairing it lands on depends on what's current when you run it, not on this document.

  2. Provisions two separate homes, not one

    A Cloudflare Pages project (or whatever it picked) for your built frontend files, and a Render or Fly.io service (or whatever it picked) for your always-on backend process. These are two unrelated accounts under the hood, each with its own dashboard and its own URL — nothing connects them automatically.

  3. Writes host-specific config, not application code

    A Dockerfile, render.yaml, or wrangler.toml — instructions the host reads to know how to build and run what your frontend/backend teammates already wrote. This step never touches your actual source files.

  4. Wires the frontend to this environment's backend URL

    This is the step it's easy to assume happens by magic — it doesn't. The frontend's code needs to know where the backend actually lives, and that's normally an environment variable (e.g. API_BASE_URL) baked in at build time. The staging frontend build gets the staging backend's URL; later, the production build gets the production URL. Skip this and staging deploys successfully but silently calls nothing, which looks like a broken site rather than a config problem.

  5. Uploads each piece to its own host

    For a static host, typically a CLI push (wrangler deploy) that copies files onto an edge network in many cities at once. For a backend host, typically a git push or CLI deploy that builds a container and starts a single running process somewhere. Each returns its own URL, scoped to "staging" or "preview" — separate from whatever production domain shows up later.

  6. Reports the staging URL, then stops

    Nothing promotes automatically. This is the pause from Section 08 Step 6 — the point where you click through the actual staging URL yourself before anything reaches a real visitor.

Phase 2 is shorter mechanically, but "promote to production" means something slightly different per host, which is worth not glossing over: for a static host it's often literally redeploying the same already-built files to a production alias or branch; for a backend host it's often flipping a service from "preview" to the one bound to your real domain, or deploying that same container to a production-tier service. Either way, no code gets regenerated at this point — only which environment serves the build that already passed your review. If it needs an account, a payment method, or a token from you to do this, it will stop and ask, the same as Phase 1.

Make it scale, not just work

"Working" and "scalable" are different bars. A hook — a command Claude Code runs automatically at a certain point, like right after a file is edited — catches the gap early instead of at launch. It can even block a subagent from finishing until the problem is fixed.

The hook runs automatically after every edit — you don't have to remember to check.
.claude/agents/frontend-html.md (add to frontmatter) 
hooks:
  PostToolUse:
    - matcher: "Edit|Write"
      hooks:
        - type: command
          command: "npx eslint src/frontend --max-warnings 0"

For frontend-cljs, swap the command for clj-kondo --lint src — same hook, same trigger, just the linter that matches the language.

Three scale-specific things worth checking before you call a generated site "done":

  • Performance budget: ask the QA subagent to run Lighthouse and flag any page scoring below a threshold you set — image weight is the usual culprit on generated sites.
  • Accessibility: an axe-core pass on every page catches missing alt text and contrast issues before a human ever looks.
  • Statelessness: if the backend teammate is stashing anything in memory between requests (session data, counters), ask it explicitly whether that survives a restart or a second server instance — a "works on my machine" API often doesn't scale past one process.
